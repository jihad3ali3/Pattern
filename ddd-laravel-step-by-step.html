DDD في Laravel 13: شرح خطوة بخطوة مع مثال كامل

نبني مثال حقيقي: نظام قبول جامعي مبسّط. الطالب يقدّم على برنامج دراسي، والجامعة تقبل أو ترفض، والمقاعد محدودة، وبعد القبول يوصله إشعار. كل خطوة: الفكرة بكلام بسيط، ثم لماذا، ثم الكود. (الكود نموذج توضيحي، جرّبه في مشروعك قبل الاعتماد.)

الخطوة ٠: لماذا نحتاج DDD أصلاً؟ (المشكلة)

الطريقة التقليدية: كل المنطق داخل الـ Controller. ينفع في البداية، لكن بعد شهور القواعد تتوزع وتتكرر ويصير تعديل قاعدة واحدة مخاطرة.

// ❌ الطريقة التقليدية: القواعد مبعثرة داخل الـ Controller
public function accept($id)
{
    $app = Application::find($id);
    if ($app->status !== 'submitted') abort(422);
    $program = Program::find($app->program_id);
    if ($program->seats < 1) abort(422);
    $program->seats--; $program->save();
    $app->status = 'accepted'; $app->save();
    Mail::to($app->student->email)->send(new Accepted());
}

المشاكل: لو أردت قبول الطلب من Command أو API ثاني، تنسخ القواعد. وأي مبرمج ممكن يكتب $app->status = 'accepted' مباشرة ويتجاوز كل الشروط.

هدف DDD: القواعد تعيش في مكان واحد (داخل المجال) ولا أحد يتجاوزها.

الخطوة ١: اللغة المشتركة (Ubiquitous Language)

قبل أي كود، اكتب المصطلحات مع تعريفها بالضبط. هذي الكلمات ستصير أسماء الكلاسات والدوال.

المصطلحالتعريف
Application (طلب قبول)طلب طالب للالتحاق ببرنامج. حالاته: مسودة، مُقدَّم، مقبول، مرفوض
Program (برنامج)تخصص له حد أدنى للمعدل وعدد مقاعد
Submit (تقديم)الانتقال من مسودة إلى مُقدَّم، بشرط أن المعدل يحقق الحد الأدنى
Accept (قبول)قبول طلب مُقدَّم، ويحجز مقعداً. لا يصح لو المقاعد انتهت

لماذا؟ لما تكتب $application->accept() يفهمها المبرمج وخبير الجامعة بنفس المعنى. هذا أهم جزء في DDD وأرخصه.

الخطوة ٢: تحديد السياقات (Bounded Contexts)

نقسم النظام لأجزاء، كل جزء له مصطلحاته وقواعده:

  • Admissions: الطلبات والبرامج والمقاعد. هذا هو Core Domain (قلب النظام).
  • Notifications: إرسال الإشعارات. جزء عام (Generic).

القاعدة: Admissions لا يعرف شيئاً عن Notifications. هو فقط يعلن «حصل شي» (Event)، ومن يهمه الأمر يستمع.

الخطوة ٤: قاعدة البيانات (عادية جداً)

DDD لا يغيّر الـ Migrations. الجداول عادية، والفرق في كيف نتعامل معها.

database/migrations/xxxx_create_admissions_tables.php
Schema::create('programs', function (Blueprint $t) {
    $t->id();
    $t->string('name');
    $t->decimal('min_gpa', 3, 2);
    $t->unsignedInteger('seats');
    $t->timestamps();
});

Schema::create('admission_applications', function (Blueprint $t) {
    $t->id();
    $t->foreignId('student_id')->constrained('users');
    $t->foreignId('program_id')->constrained();
    $t->decimal('gpa', 3, 2);
    $t->string('status')->default('draft');
    $t->timestamps();
});

الخطوة ٥: Value Object (المعدل Gpa)

الفكرة: بدل ما المعدل رقم عادي (ممكن يكون 9 أو -3!)، نسوّي له كلاس يرفض القيم الخاطئة. وهو غير قابل للتغيير (readonly): تنشئه مرة وما يتبدل.

لماذا؟ أي مكان في النظام يستقبل Gpa يضمن أنه صحيح بدون إعادة التحقق.

src/Domain/Admissions/ValueObjects/Gpa.php
<?php
namespace Domain\Admissions\ValueObjects;

use InvalidArgumentException;

final readonly class Gpa
{
    public function __construct(public float $value)
    {
        if ($value < 0 || $value > 5) {
            throw new InvalidArgumentException("GPA must be between 0 and 5, got {$value}");
        }
    }

    public function meets(self $minimum): bool
    {
        return $this->value >= $minimum->value;
    }
}

الخطوة ٦: Enum للحالات + الانتقالات المسموحة

الفكرة: الحالات محصورة (ما يصير status = «abc»)، والـ Enum نفسه يعرف أي انتقال مسموح.

src/Domain/Admissions/Enums/ApplicationStatus.php
<?php
namespace Domain\Admissions\Enums;

enum ApplicationStatus: string
{
    case Draft = 'draft';
    case Submitted = 'submitted';
    case Accepted = 'accepted';
    case Rejected = 'rejected';

    public function canTransitionTo(self $next): bool
    {
        return match ($this) {
            self::Draft     => $next === self::Submitted,
            self::Submitted => in_array($next, [self::Accepted, self::Rejected], true),
            default         => false, // مقبول/مرفوض: حالة نهائية
        };
    }
}

الخطوة ٧: استثناءات المجال (Domain Exceptions)

الفكرة: لما قاعدة تنكسر نرمي استثناء بإسم يشرح السبب بلغة العمل، بدل abort(422) مجهول.

src/Domain/Admissions/Exceptions/*.php (كل كلاس في ملف)
<?php
namespace Domain\Admissions\Exceptions;

use Domain\Admissions\Enums\ApplicationStatus;
use Domain\Admissions\Models\Program;
use DomainException;

final class InvalidTransition extends DomainException
{
    public static function from(ApplicationStatus $from, ApplicationStatus $to): self
    {
        return new self("Cannot move application from {$from->value} to {$to->value}");
    }
}

final class GpaBelowMinimum extends DomainException
{
    public static function for(Program $program): self
    {
        return new self("GPA is below the minimum required for {$program->name}");
    }
}

final class NoSeatsAvailable extends DomainException
{
    public static function for(Program $program): self
    {
        return new self("No seats left in {$program->name}");
    }
}

الخطوة ٨: الكيانات (Entities) بالسلوك

الفكرة: الموديل ما يكون مجرد حاوية بيانات. فيه دوال تعبّر عن أفعال العمل (submit, accept) وتحمي القواعد. هذا يمنع النموذج الفقير (Anemic Model).

Program: يحمي قاعدة المقاعد

src/Domain/Admissions/Models/Program.php
<?php
namespace Domain\Admissions\Models;

use Domain\Admissions\Exceptions\NoSeatsAvailable;
use Domain\Admissions\ValueObjects\Gpa;
use Illuminate\Database\Eloquent\Model;

class Program extends Model
{
    protected $guarded = [];

    protected function casts(): array
    {
        return ['min_gpa' => 'float'];
    }

    public function minGpa(): Gpa
    {
        return new Gpa($this->min_gpa);
    }

    public function reserveSeat(): void
    {
        if ($this->seats < 1) {
            throw NoSeatsAvailable::for($this);
        }
        $this->decrement('seats');
    }
}

AdmissionApplication: الـ Aggregate Root

هذا «الجذر»: كل تغيير على حالة الطلب يمر من خلاله فقط. لاحظ أن الحالة تتغير داخل دالة خاصة transitionTo تتحقق من القاعدة.

src/Domain/Admissions/Models/AdmissionApplication.php
<?php
namespace Domain\Admissions\Models;

use Domain\Admissions\Enums\ApplicationStatus;
use Domain\Admissions\Events\ApplicationAccepted;
use Domain\Admissions\Events\ApplicationSubmitted;
use Domain\Admissions\Exceptions\GpaBelowMinimum;
use Domain\Admissions\Exceptions\InvalidTransition;
use Domain\Admissions\ValueObjects\Gpa;
use Illuminate\Database\Eloquent\Model;

class AdmissionApplication extends Model
{
    protected $guarded = [];

    protected function casts(): array
    {
        return ['status' => ApplicationStatus::class];
    }

    public function gpa(): Gpa
    {
        return new Gpa((float) $this->attributes['gpa']);
    }

    /** تقديم الطلب: يتحقق من المعدل ثم ينقل الحالة */
    public function submit(Program $program): void
    {
        if (! $this->gpa()->meets($program->minGpa())) {
            throw GpaBelowMinimum::for($program);
        }

        $this->transitionTo(ApplicationStatus::Submitted);
        $this->save();

        ApplicationSubmitted::dispatch($this);
    }

    public function accept(): void
    {
        $this->transitionTo(ApplicationStatus::Accepted);
        $this->save();

        ApplicationAccepted::dispatch($this);
    }

    public function reject(): void
    {
        $this->transitionTo(ApplicationStatus::Rejected);
        $this->save();
    }

    private function transitionTo(ApplicationStatus $next): void
    {
        if (! $this->status->canTransitionTo($next)) {
            throw InvalidTransition::from($this->status, $next);
        }
        $this->status = $next;
    }
}

ملاحظة صادقة: Eloquent لا يمنع أحداً من كتابة $app->status = ... من الخارج. DDD في لارافل اتفاق فريق (Convention) أكثر منه منع تقني. وللتشديد ممكن تخلّي status خارج $fillable وتراجع الكود في المراجعات.

الخطوة ٩: الأحداث (Domain Events)

الفكرة: الحدث يعلن شي «حصل» (بصيغة الماضي). هو الجسر بين السياقات. أضفنا ShouldDispatchAfterCommit حتى لا يُرسل الحدث إلا بعد نجاح الـ Transaction (لو فشلت العملية ما يوصل إشعار كاذب).

src/Domain/Admissions/Events/ApplicationAccepted.php
<?php
namespace Domain\Admissions\Events;

use Domain\Admissions\Models\AdmissionApplication;
use Illuminate\Contracts\Events\ShouldDispatchAfterCommit;
use Illuminate\Foundation\Events\Dispatchable;

final class ApplicationAccepted implements ShouldDispatchAfterCommit
{
    use Dispatchable;

    public function __construct(public readonly AdmissionApplication $application) {}
}
// ApplicationSubmitted بنفس الشكل

الخطوة ١٠: DTO (نقل البيانات)

الفكرة: بدل تمرير Request أو مصفوفة غامضة للمجال، نمرر كائناً واضحاً بأنواع محددة. المجال ما يعرف شي عن HTTP.

src/Domain/Admissions/DataTransferObjects/SubmitApplicationData.php
<?php
namespace Domain\Admissions\DataTransferObjects;

final readonly class SubmitApplicationData
{
    public function __construct(
        public int $studentId,
        public int $programId,
        public float $gpa,
    ) {}
}

الخطوة ١١: Actions (حالات الاستخدام)

الفكرة: كل Action = سيناريو عمل واحد. وظيفته التنسيق: يجلب الكائنات، يفتح Transaction، وينادي دوال المجال. المنطق نفسه (القواعد) يبقى في الموديل.

تقديم طلب

src/Domain/Admissions/Actions/SubmitApplicationAction.php
<?php
namespace Domain\Admissions\Actions;

use Domain\Admissions\DataTransferObjects\SubmitApplicationData;
use Domain\Admissions\Enums\ApplicationStatus;
use Domain\Admissions\Models\AdmissionApplication;
use Domain\Admissions\Models\Program;
use Domain\Admissions\ValueObjects\Gpa;
use Illuminate\Support\Facades\DB;

final class SubmitApplicationAction
{
    public function execute(SubmitApplicationData $data): AdmissionApplication
    {
        return DB::transaction(function () use ($data) {
            $program = Program::findOrFail($data->programId);

            $application = AdmissionApplication::create([
                'student_id' => $data->studentId,
                'program_id' => $program->id,
                'gpa'        => (new Gpa($data->gpa))->value, // يتحقق من الصحة
                'status'     => ApplicationStatus::Draft,
            ]);

            $application->submit($program);

            return $application;
        });
    }
}

قبول طلب (يلمس Aggregateين: الطلب والبرنامج)

هنا قاعدة مهمة: كل Aggregate يحمي نفسه، والـ Action ينسّق بينهما داخل Transaction واحدة. نستخدم lockForUpdate حتى لو قبل مديران طلبين في نفس اللحظة ما ينحجز مقعد زيادة.

src/Domain/Admissions/Actions/AcceptApplicationAction.php
<?php
namespace Domain\Admissions\Actions;

use Domain\Admissions\Models\AdmissionApplication;
use Domain\Admissions\Models\Program;
use Illuminate\Support\Facades\DB;

final class AcceptApplicationAction
{
    public function execute(int $applicationId): AdmissionApplication
    {
        return DB::transaction(function () use ($applicationId) {
            $application = AdmissionApplication::lockForUpdate()->findOrFail($applicationId);
            $program     = Program::lockForUpdate()->findOrFail($application->program_id);

            $program->reserveSeat();   // يرمي NoSeatsAvailable لو ما فيه مقاعد
            $application->accept();    // يرمي InvalidTransition لو الحالة غلط

            return $application;
        });
    }
}

الخطوة ١٢: التواصل بين السياقات (Listener)

الفكرة: سياق Notifications يستمع لحدث Admissions. لو حذفنا Notifications كله، Admissions يشتغل بدون تغيير. لارافل تربط الـ Listener بالحدث من نوع الـ Type-hint في handle().

src/Domain/Notifications/Listeners/NotifyStudentOfAcceptance.php
<?php
namespace Domain\Notifications\Listeners;

use Domain\Admissions\Events\ApplicationAccepted;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Support\Facades\Mail;

final class NotifyStudentOfAcceptance implements ShouldQueue
{
    public function handle(ApplicationAccepted $event): void
    {
        $student = \App\Models\User::find($event->application->student_id);

        Mail::to($student->email)->send(new \App\Mail\ApplicationAcceptedMail());
    }
}

الاكتشاف التلقائي افتراضياً يشتغل لمجلد app/Listeners. بما أن Listeners عندنا داخل src/Domain نضيف المسار في bootstrap/app.php (تحقق من الصيغة في توثيق 13):

bootstrap/app.php
return Application::configure(basePath: dirname(__DIR__))
    ->withEvents(discover: [base_path('src/Domain/*/Listeners')])
    // ...
    ->withExceptions(function (Exceptions $exceptions) {
        // نحوّل أخطاء المجال إلى 422 مفهومة بدل 500
        $exceptions->render(fn (\DomainException $e) =>
            response()->json(['message' => $e->getMessage()], 422)
        );
    })->create();

الخطوة ١٣: طبقة الويب (Controller رفيع)

الـ Controller يفعل ثلاثة أشياء فقط: يستقبل، ينادي Action، يرد. لا قواعد هنا.

app/Http/Requests/SubmitApplicationRequest.php
class SubmitApplicationRequest extends FormRequest
{
    public function rules(): array
    {
        return [
            'program_id' => ['required', 'exists:programs,id'],
            'gpa'        => ['required', 'numeric', 'between:0,5'], // تحقق شكلي فقط
        ];
    }
}
app/Http/Controllers/ApplicationController.php
class ApplicationController extends Controller
{
    public function store(SubmitApplicationRequest $request, SubmitApplicationAction $submit)
    {
        $application = $submit->execute(new SubmitApplicationData(
            studentId: $request->user()->id,
            programId: $request->integer('program_id'),
            gpa: $request->float('gpa'),
        ));

        return response()->json($application, 201);
    }

    public function accept(int $id, AcceptApplicationAction $accept)
    {
        return response()->json($accept->execute($id));
    }
}
routes/api.php
Route::middleware('auth:sanctum')->group(function () {
    Route::post('/applications', [ApplicationController::class, 'store']);
    Route::post('/applications/{id}/accept', [ApplicationController::class, 'accept']);
});

الفرق بين نوعي التحقق: الـ FormRequest يتحقق من شكل المدخلات (هل رقم؟). المجال يتحقق من قواعد العمل (هل المعدل يكفي البرنامج؟). لا تخلطهما.

الخطوة ١٤: الاختبار (هنا تظهر الفائدة)

قواعد المجال تُختبر بدون HTTP وبسرعة. (Pest)

use Domain\Admissions\ValueObjects\Gpa;

it('rejects an invalid gpa', function () {
    new Gpa(7);
})->throws(InvalidArgumentException::class);

it('cannot accept a draft application', function () {
    $app = AdmissionApplication::factory()->create(['status' => ApplicationStatus::Draft]);

    expect(fn () => $app->accept())->toThrow(InvalidTransition::class);
});

it('does not accept when no seats left', function () {
    $program = Program::factory()->create(['seats' => 0]);
    $app = AdmissionApplication::factory()->create([
        'program_id' => $program->id,
        'status' => ApplicationStatus::Submitted,
    ]);

    expect(fn () => (new AcceptApplicationAction)->execute($app->id))
        ->toThrow(NoSeatsAvailable::class);
});

الصورة الكاملة: مسار طلب «قبول»

  1. POST /applications/5/accept يصل لـ Controller (ويب فقط).
  2. الـ Controller ينادي AcceptApplicationAction (تنسيق + Transaction).
  3. الـ Action ينادي $program->reserveSeat() و$application->accept() (قواعد المجال).
  4. الموديل يرمي استثناء لو القاعدة انكسرت، فيتحول لـ 422 تلقائياً.
  5. بعد نجاح الـ Commit ينطلق ApplicationAccepted.
  6. Listener في سياق Notifications يرسل الإيميل في الـ Queue.

أين أضع الكود؟ (جدول القرار)

السؤالالمكان
قاعدة عمل تخص كياناً واحداً؟دالة داخل الموديل
قيمة لها قواعد (معدل، مبلغ، إيميل)؟Value Object
سيناريو كامل يلمس أكثر من كيان أو يحتاج Transaction؟Action
حالات محدودة وانتقالات؟Enum
شي حصل ويهم سياقاً آخر؟Event + Listener
التحقق من شكل المدخلات؟FormRequest
استعلامات متكررة؟Query Builder مخصص (أو #[UseEloquentBuilder] في 13)

ما الذي تركته عمداً؟

ما استخدمت Repository: مع Eloquent غالباً زيادة تعقيد، وأضفه فقط لو احتجت عزل المجال عن مصدر بيانات خارجي. وما غطيت CQRS أو Event Sourcing لأنها مواضيع متقدمة ما تلزم أغلب المشاريع.
